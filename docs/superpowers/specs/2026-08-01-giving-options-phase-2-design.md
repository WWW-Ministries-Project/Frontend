# Giving Options Phase 2 — Donor Checkout, Webhook, Contributions

Status: approved, not yet implemented.
Date: 2026-08-01.
Phase 1 (giving options + Paystack subaccounts) shipped in `Frontend@47193e2` and
`Backend@f6f8a66`. See `docs/GIVING_OPTIONS_BACKEND_CONTRACT.md` for phase 1.

## Goal

Make money actually arrive. A member opens the mobile Give screen, picks a giving
option, pays through Paystack, and the payment settles into that option's
subaccount. A contribution record is written, a receipt is emailed, and finance
staff can see every contribution in the web dashboard.

## Architecture

The Backend owns everything that touches money. Mobile is the only donor surface.
The web dashboard is read-only reporting over contributions.

No new service and no queue. The Paystack webhook and an on-demand verify
endpoint both converge on a single idempotent settle function, so a payment
settles exactly once regardless of which path observes it first.

Deliberately unchanged from phase 1: every giving option still routes 100% of its
payments to its own settlement account (`percentage_charge = 100`,
`bearer = "subaccount"`). Nothing is split.

## Data model

New table `givingContribution`.

| Column | Type | Notes |
|---|---|---|
| `id` | `VARCHAR(191)` | cuid, matches the other finance tables |
| `reference` | `VARCHAR(191)` unique | generated by us, passed to Paystack |
| `giving_option_id` | `VARCHAR(191)` | FK → `givingOption`, `ON DELETE RESTRICT` |
| `giving_option_name` | `VARCHAR(191)` | snapshot at time of giving |
| `subaccount_code` | `VARCHAR(191)?` | snapshot of where it settled |
| `user_id` | `INT?` | donor, **no foreign key** |
| `donor_name` | `VARCHAR(191)` | snapshot |
| `donor_email` | `VARCHAR(191)` | snapshot, receipt target |
| `amount` | `INT` | **minor units (pesewas)** |
| `currency` | `VARCHAR(191)` | defaults `GHS` |
| `status` | `VARCHAR(191)` | `pending` \| `success` \| `failed` \| `abandoned` |
| `channel` | `VARCHAR(191)?` | `card` / `mobile_money`, reported by Paystack |
| `paid_at` | `DATETIME?` | set at settlement |
| `paystack_response` | `LONGTEXT?` | raw verified payload |
| `receipt_sent_at` | `DATETIME?` | non-null ⇒ receipt already emailed |
| `branch_id` | `INT?` | FK → `branch`, `ON DELETE SET NULL` |
| `created_at` | `DATETIME` | |
| `updated_at` | `DATETIME` | |

Indexes: `reference`, `giving_option_id`, `user_id`, `status`, `branch_id`,
`created_at`.

### Why these choices

**`amount` is an integer in minor units.** Paystack transacts in minor units, and
binary floats cannot represent decimal currency exactly. `bankAccountConfig.percentage`
is a `Float` because it is a ratio; money in motion is not a ratio. Mobile
multiplies the entered GHS amount by 100; every display divides by 100.

**`user_id` has no foreign key.** Same reasoning as `givingOption.created_by`: a
deleted user must not be able to cascade into, or block deletion of, a financial
record. The donor identity is an audit breadcrumb, not a relational dependency.

**`giving_option_name`, `donor_name`, `donor_email` and `subaccount_code` are
snapshots.** Renaming a giving option or a member changing their email must not
retroactively rewrite what a past receipt said. `ON DELETE RESTRICT` on
`giving_option_id` is belt-and-braces: options are soft-archived, never deleted.

**`paystack_response` is retained.** Chargeback and reconciliation disputes are
resolved against what the processor actually said, not against our summary of it.

## Endpoints

Base `/givingoption`, extending the phase 1 router. All routes require a bearer
token except the webhook.

| Method | Path | Permission | Notes |
|---|---|---|---|
| GET | `/available` | auth only | Options offerable to this member |
| POST | `/initialize` | auth only | Starts a payment |
| GET | `/verify/:reference` | auth only | On-demand settle |
| GET | `/my-contributions` | auth only | Caller's own history, paginated |
| GET | `/contributions` | `Giving:view` | Admin list, paginated |
| POST | `/paystack-webhook` | public, signature-verified | `charge.success` |

Giving requires only authentication — any member may give. `Giving:manage` stays
on configuration, as in phase 1. Because `Giving` falls back to `Financials`
(`PERMISSION_KEY_ALIASES`, `DOMAIN_FALLBACKS`), anyone who can view Financials can
view contributions until an admin sets `Giving` explicitly.

**Route ordering hazard.** Phase 1 registers `GET /:id` last, at
`Backend/src/modules/finance/GivingOption/route.ts:275`. Express matches in
registration order, so `/available`, `/contributions`, `/my-contributions` and
`/verify/:reference` must all be registered **above** it. Registered below, they
would be swallowed by `/:id` and return "giving option not found" for a literal id
of `"available"` — a confusing failure that looks like a data problem rather than
a routing one.

### `GET /available`

Returns non-archived options where `is_active = true`, `paystack_synced_at IS NOT
NULL`, and `branch_id = <member's branch> OR branch_id IS NULL`.

Org-wide funds are created once with no branch and are visible to everyone;
branch-specific options stay local. A drifted option (`paystack_synced_at IS
NULL`) is withheld — it cannot reliably receive money, so offering it would take a
payment we cannot route.

### `POST /initialize`

Body: `{ giving_option_id, amount }` where `amount` is minor units.

1. Load the option, re-checking the `/available` predicate against the caller.
2. Validate `amount` is an integer at or above the minimum (GHS 1 = `100`).
3. Insert a `pending` contribution with a generated `reference`.
4. Call Paystack `POST /transaction/initialize` with `subaccount`,
   `bearer: "subaccount"`, `reference`, `amount`, `currency`, the donor's email,
   and `callback_url` set to the mobile deep link.
5. Return `{ checkoutUrl, reference }`.

If Paystack rejects the init, the pending row is marked `failed` and the existing
`PaystackError` mapping (422 rejected / 502 unreachable) is returned unchanged.

### `POST /paystack-webhook`

Public by necessity. Authenticated by HMAC signature, not by a token.

## Settlement

The webhook and `/verify/:reference` both call one function,
`settleContribution(reference, paystackData)`:

1. Load by `reference`. Unknown reference → ack `200` and log. Returning an error
   makes Paystack retry indefinitely for a payment we will never recognise.
2. Already `success` → return immediately. No writes, no second receipt.
3. Compare Paystack's reported `data.amount` against the stored pending amount.
   On mismatch, record the amount Paystack actually collected and flag the row for
   review rather than accepting the client-supplied figure.
4. Mark `success`; set `paid_at`, `channel`, and `paystack_response`.
5. Send the receipt, after the database commit, inside a `try`/`catch`.

Step 5 must never fail settlement. An email outage leaves `receipt_sent_at` null
and logs; the money is still recorded as received.

## Webhook signature verification

Compute HMAC SHA512 over the **raw request body** using the Paystack secret key,
and compare against the `x-paystack-signature` header in constant time. Reject with
`401` before parsing anything.

`express.json()` is mounted globally at `Backend/index.ts:46`, so the raw body is
already discarded by the time the route handler runs. Fix by adding a `verify`
callback to that existing `express.json()` call which stashes the buffer on
`req.rawBody`. This is preferred over mounting `express.raw` on the webhook path
because it does not depend on router mount order, which is easy to break later.

The secret key is read only through `resolvePaystackCredentials`, per phase 1.
Nothing else reads `PAYSTACK_SECRET_KEY` directly, and it is never returned to any
client.

## Receipt email

New template `Backend/src/utils/mail_templates/givingReceiptTemplate.ts`, built on
the existing `unifiedEmailTemplate` and sent through `sendEmail`.

Contents: giving option name, amount and currency, date paid, payment channel, and
the transaction reference.

`receiptConfig` is not involved. Despite the name it is a `{id, name, description,
branch_id}` lookup list like `paymentConfig`, not a template store.

## Error handling

| Situation | Behaviour |
|---|---|
| Paystack rejects init | Pending row → `failed`; 422 with Paystack's message passed through |
| Paystack unreachable at init | Pending row → `failed`; 502 |
| Donor cancels in the browser | Row stays `pending`. **Not** auto-failed — the payment may still complete and the webhook will settle it |
| Bad webhook signature | `401`, nothing parsed, nothing written |
| Webhook for unknown reference | `200` ack plus a log, so Paystack stops retrying |
| Duplicate webhook delivery | No-op via the already-`success` guard |
| Concurrent webhook and verify | Unique constraint on `reference` plus the status guard means one settles, the other no-ops |
| Receipt email fails | Settlement stands; `receipt_sent_at` stays null; logged |

Backend, then Frontend, then Mobile. Backend must be live before either client
ships code depending on the new shapes. Merging to Backend `main` runs
`prisma migrate deploy` against the dev database immediately.

## Out of scope

Named so they are not assumed: pledge redemption linking, recurring or scheduled
giving, refunds and reversals, a public web giving page, and anonymous giving.

## Related security note

`Frontend/.env` currently holds `REACT_APP_PAYSTACK_SECRETE_KEY=sk_test_…`.
`vite.config.js` inlines every `process.env` value into the built bundle, so any
secret key placed there is readable by anyone who loads the site. The key belongs
only in `Backend/.env`. The line must be removed, and no `sk_live_` key may ever
be added to a `REACT_APP_*` variable. `REACT_APP_PAYSTACK_PUBLIC_KEY` (`pk_test_`)
is fine — public keys are intended for the browser.
